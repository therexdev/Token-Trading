# User security requirements and implementation plan

Prepared 2026-09-21. This is a release plan, not a certification that the application is safe. Code changes do not protect an older deployed contract. Production contract bytecode, hosting settings, operator keys, and logs have not been inspected or changed.

The implementation starts from Token-Trading `9b3fdbfed4ac348c8ea8e2e34b82623f719b3975`. The companion wallet change starts from koin-vault `d968a2dcd8e64eee627d1b1d2329ce51498bbab9`. The signing-service review covers discover-koinos `c8dc7959c53e9bbce72d4654ddd934fb3b602fea`; that service is not modified by these changes.

## Requirements, in priority order

“Implemented” below means code and local tests, not production deployment. P0 items precede renewed reliance on the affected settlement flows. P1 items precede treating the wider authentication and API review as complete. P2 items are continuing hardening and operational work.

| ID | Priority | Requirement and acceptance criteria | Owner / state |
| --- | --- | --- | --- |
| SEC-01 | P0 | A token, router, or authorization callback cannot re-enter any state-changing orderbook or launchpad method. Test repeated settlement, cross-method calls, preserved owner authorization, and rollback followed by a successful retry. | Contracts: implemented; real-node rehearsal and deployment pending. |
| SEC-02 | P0 | Show success only after canonical block inclusion and a matching non-reverted transaction receipt. Missing receipts, RPC failures, and confirmation timeouts retain the transaction ID and an explicit pending state. Status checks must never broadcast again. | Trade UI: implemented across order, cancellation, market creation, launch creation, contribution, and claims. |
| SEC-03 | P1 | Wallet credentials travel in HTTPS JSON bodies. New pairing URLs put credentials in a fragment and scrub it after reading. Preserve origin binding, passkey approval, expiry, disconnect, and request isolation. Reject silent protocol downgrade. | Trade + Vault: implemented for the new protocol; deploy the wallet first. Legacy client migration remains open. |
| SEC-04 | P1 | Deployment always encrypts credentials and content and validates the server certificate, including retry attempts. No plaintext fallback. Workflow inputs must not be interpolated as shell code. | Hostinger workflow: FTPS with strict verification implemented. Actual host certificate/connection check pending. |
| SEC-05 | P1 | Untrusted project links can only navigate to absolute HTTP(S) URLs without embedded credentials or control characters. Continue React escaping; do not render supplied HTML. | Trade UI: implemented. The gateway already restricts saved links to HTTP(S). |
| SEC-06 | P1 | Signed API proofs bind the exact operation payload, account, action, endpoint, origin/audience, chain where applicable, expiry, and a one-time nonce. Consuming a nonce must be atomic and survive the required process topology. A captured proof must fail on replay or altered fields. | Signing gateway + all proof clients: open. Current `verifyProof` signs only action and timestamp and accepts reuse within five minutes. |
| SEC-07 | P1 | Global token branding requires proven token-controller or registry-owner authority. Authentication alone must not let the first caller claim another token's logo. Test first-write hijacking, owner changes, replacement, and concurrent writes. | Signing gateway: open. `launchpadLogo` currently uses first-writer ownership. Define and migrate the branding authority policy before enabling unrestricted first writes. |
| SEC-08 | P1 | Logout, account compromise, and operator revocation invalidate signer sessions server-side. Bind each session to its verified account, audience, allowed capability, and finite expiry. Test expiry, tampering, wrong account, revocation, and late responses. | Signing gateway + Trade: open. Current hosted signer tokens expire but have no per-session revocation endpoint; local logout alone cannot revoke a copied token. This is not evidence of a credential-free login bypass. |
| SEC-09 | P1 | Inventory custody, sponsor, contract-upgrade, and deployment keys. Require protected storage and encrypted backups, restricted access, rotation, and a tested recovery procedure. Distinguish Google server custody from user-controlled wallet signing in product copy. | Service/operations: open verification. Google keys use AES-GCM in source; token/collection upgrade keys are written to owner-only JSON files. Production disk/backup encryption is unverified. |
| SEC-10 | P1 | Every sensitive API action independently validates its credential and object ownership. Keep Vault's origin and passkey checks on both new POST and legacy routes. Require safe cross-origin behavior and JSON parsing; if cookie authentication is added, add and test CSRF protection before using it. | Vault POST controls tested. Gateway ownership/authentication regression coverage remains open. Current Trade requests use explicit tokens/proofs, not ambient login cookies. |
| SEC-11 | P1 | Bound request bytes, time, concurrent work, upload storage, and sponsored spending. Verify proxy trust and rate limits under the actual process/replica topology; malformed or unavailable dependencies fail without signing or losing funds. | Existing limits identified; production and multi-process verification open. |
| SEC-12 | P2 | Uploads use server-generated names, bounded raster formats, safe serving types, and non-executable storage. Test corrupt/polyglot images, decoded pixel/resource limits, quotas, and ownership. | Gateway already enforces byte limits, magic-byte format checks, and rejects SVG uploads. Decoder/resource and storage controls need further verification. |
| SEC-13 | P1 | Each release passes security regressions and production builds; independently review contract changes, record WASM hashes, protect the release branch, and verify deployed code. Rebuild from trusted dependencies and monitor applicable advisories. | Repeatable CI added. Branch rules, independent review, and deployment attestation are operator gates. |
| SEC-14 | P2 | Verify live TLS and browser security headers on every served entry point; redact credentials from proxy/application/error logs. Keep a CSP compatible with required Google and protobuf behavior and test changes before tightening it. | Header configuration exists in `.htaccess`; enforcement on the actual host and log redaction remain unverified. |
| SEC-15 | P1 | Define incident ownership, alerts for abnormal settlements/signing, sponsor depletion and failed keeper work, and a recovery drill. Preserve evidence without logging bearer tokens or private keys. | Operations: open. |
| SEC-16 | P2 | Explain permissionless-token and creator risk at purchase/trade decisions. Show contract identity, network, exact amounts, allowances, and sale/lock terms. Listing, a logo, and a passing interface check must not be presented as token verification. | Product + protocol review: open. A reentrancy lock does not make a dishonest token safe or guarantee that it will transfer. |

No new password database is needed for this application. Its flows use Google, wallet signatures, and passkeys. The reviewed app does not establish a user-input path to SQL, operating-system commands, or arbitrary runtime code; those categories remain subject to review when new server or plugin functionality is added.

## Implemented behavior

Both contracts acquire a storage-backed lock before any mutating logic or authority check, and release it on successful completion. Every mutating ABI entry point is covered. Koinos transaction rollback must roll back the lock on failure. The orderbook uses new storage space 6; the launchpad uses space 4. Existing state objects, entry points, and protobuf schemas are unchanged. Read methods stay available. Nested legitimate mutations are also rejected, so integrations must be exercised during the upgrade rehearsal.

The transaction UI checks both inclusion and the actual block receipt. A timeout or unavailable receipt cannot reach the success path or trigger post-confirmation metadata work. An explicit reverted receipt is an error. An unconfirmed transaction remains visible with its ID, explorer link, and “Check status” action; checking only reads the same transaction. This indicates inclusion, not irreversible finality. The pending notification currently lasts within the page session; a full transaction-history/recovery experience across reloads is a separate product requirement. A failed wallet/broadcast call before a usable handle is returned can still require checking the wallet directly.

The paired-wallet client requests `protocolVersion: 2`, validates the returned wallet origin and matching fragment credentials, and uses POST for status polling. The companion Vault patch adds POST readers with the same authorization policy, understands and scrubs fragment links, and preserves fragments when its frontend proxy rewrites the wallet origin. Vault's own polling also uses POST. Older clients retain their existing GET/query protocol during migration; the URL-secret issue is not closed ecosystem-wide until those clients migrate and the legacy routes are retired. Old sessions should be revoked or allowed to expire after reviewing access-log exposure. URL fragments still contain bearer credentials and must not be shared or logged.

All three deployment attempts now require explicit FTPS with strict certificate verification. A hostname without a matching valid certificate causes a deployment failure. The workflow no longer permits an `FTP_PROTOCOL=ftp` override. The server value is passed through the environment and validated as a hostname instead of interpolated into shell source.

## Validation

- `npm run test:contracts`: seven WASM tests pass, including all 13 mutating ABI methods, malicious transfer/authority callbacks, duplicate payout prevention, owner checks, failed-transfer rollback, and subsequent successful transactions. The test host models atomic rollback and token balances; it is not a live Koinos node or an independent audit.
- `cd frontend && npm test`: 41 tests pass, covering transaction receipt failure/pending/success handling, safe rechecking, wallet transport and downgrade rejection, link protocols, and existing sign-in/trading regressions.
- `npm run build` in `contract/` and `launchpad/`: both release builds complete, including protobuf/dispatcher generation and WebAssembly MVP verification. A local gRPC-distributed protoc was supplied on PATH because direct GitHub release downloads were unavailable in the review environment. Generated source schemas/dispatchers are unchanged; unrelated ABI JSON generator-format changes are excluded from the patch.
- `cd frontend && npm run build`: passes TypeScript and Vite production compilation. Vite retains its existing large-bundle warning.
- Companion Vault `npm run pretest`: all 17 security/session/wallet test programs pass, including real local HTTP server and proxy checks for POST status, wrong origins, missing credentials, wallet-only pending access, and legacy compatibility. External chain/RPC operations in these tests use fixtures.
- `npm audit --omit=dev`: zero reported runtime advisories for the current Trade and Vault dependency locks at review time. This is an advisory lookup, not evidence that dependencies contain no defects.

## Rollout gates and order

1. Compare deployed contract code and storage layout with the reviewed versions. Identify the upgrade authorities, current escrow balances, active orders/launches, outstanding claims, and keeper version. If vulnerable code is live, coordinate containment before continuing to direct deposits to it. Hiding a frontend action cannot disable direct contract calls.
2. Complete independent review and a real-node staging or fork rehearsal of both contract upgrades. Exercise existing orders and launches, ordinary Google/Kondor/Vault flows, failed transfers, callback reentry, all liquidity and locked-claim paths, sequential operations in one transaction, and keeper settlement. Measure additional storage/mana costs. Verify contract rollback and authorization behavior with the real runtime.
3. Deploy the Vault backend and frontend proxy/client support first. Confirm protocol 2 on the production wallet origin, POST CORS and origin checks, QR/open-wallet behavior, approval, denial, expiry, and disconnect. Retain a documented migration window for other applications. Never work around a failed protocol check by sending the secret in a query string.
4. Execute the separately approved contract upgrade or migration, preserve existing escrow/claim accounting, and verify the exact deployed bytecode and state. Update configured addresses and the keeper only if the release requires them. Do not roll back to vulnerable bytecode as a routine recovery action.
5. Release the Trade frontend through verified FTPS after the wallet and contract gates. Confirm actual TLS/CSP/anti-framing headers, the correct network and addresses, non-reverted receipt lookup on supported RPCs, and Google/Kondor/Vault end-to-end flows. The default-branch merge triggers the existing frontend deployment workflow; review that timing before merging.
6. Monitor settlement and API behavior, retain release hashes and test evidence, complete the signer-service requirements SEC-06 through SEC-09, and retire legacy wallet URL credentials after all clients migrate. Do not mark the wider security review complete while these requirements remain open.
